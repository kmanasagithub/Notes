# Spring Data JPA Projections

# What is Projection?

## Introduction

In real-world applications, we often do not need all the columns of a database table.

Consider a Patient table:

| id | name | email | gender | birthDate | bloodGroup | createdAt |
| -- | ---- | ----- | ------ | --------- | ---------- | --------- |

Suppose we only need:

```text
id
name
```

for displaying a patient list.

Fetching all columns wastes:

* Database resources
* Network bandwidth
* Application memory

To solve this problem, Spring Data JPA provides **Projections**.

---

## Definition

A Projection is a mechanism in Spring Data JPA that allows us to retrieve only the required fields from the database instead of loading the entire entity.

In simple words:

> Projection means fetching only the columns we need.

---

# Why Do We Need Projections?

Without projections:

```java
List<Patient> patients =
        patientRepository.findAll();
```

Hibernate executes:

```sql
SELECT
id,
name,
email,
gender,
birth_date,
blood_group,
created_at
FROM patient;
```

Even if we only display:

```java
patient.getName();
```

all columns are fetched.

This is inefficient.

---

## With Projection

```java
@Query("""
select p.id as id,
       p.name as name
from Patient p
""")
List<IPatientInfo> getAllPatientsInfo();
```

Hibernate executes:

```sql
SELECT
id,
name
FROM patient;
```

Only required columns are fetched.

This improves performance.

---

# Real World Analogy

Imagine going to a restaurant.

You only want:

```text
Rice
Curry
```

But the waiter brings:

```text
Rice
Curry
Soup
Dessert
Ice Cream
Juice
```

This is similar to fetching an entire entity.

Projection means:

```text
Bring only what I asked for.
```

# Why Not Return Entity Directly?

Suppose Patient entity becomes:

```java
@Entity
public class Patient {

    private Long id;

    private String name;

    private String email;

    private String medicalHistory;

    private String insuranceNumber;

    private String emergencyContact;

    private byte[] profilePicture;
}
```

Returning:

```java
List<Patient>
```

may fetch all fields.

Even if we only need:

```java
id
name
```

This wastes memory and processing time.

---

# Types of Projections

Spring Data JPA supports three types of projections.

1. Interface-Based Projection
2. Class-Based Projection
3. Dynamic Projection

---

# 1. Interface-Based Projection

This is the most commonly used projection.

Example:

```java
public interface IPatientInfo {

    Long getId();

    String getName();

    String getEmail();
}
```

Repository:

```java
@Query("""
select p.id as id,
       p.name as name,
       p.email as email
from Patient p
""")
List<IPatientInfo> getAllPatientsInfo();
```

---

## How It Works

Spring looks at:

```java
getId()

getName()

getEmail()
```

and automatically maps them to:

```text
id
name
email
```

columns.

Spring creates an implementation behind the scenes.

You never write:

```java
class PatientInfoImpl
```

Spring generates it automatically.

---

## Example Usage

```java
List<IPatientInfo> patients =
        patientRepository.getAllPatientsInfo();

patients.forEach(patient -> {

    System.out.println(patient.getId());

    System.out.println(patient.getName());

    System.out.println(patient.getEmail());
});
```

---

# 2. Class-Based Projection

Instead of an interface, we create a DTO.

Example:

```java
public class PatientInfoDTO {

    private Long id;

    private String name;

    public PatientInfoDTO(
            Long id,
            String name) {

        this.id = id;
        this.name = name;
    }
}
```

Repository:

```java
@Query("""
select new
com.example.dto.PatientInfoDTO(
       p.id,
       p.name
)
from Patient p
""")
List<PatientInfoDTO> getPatients();
```

---

## How It Works

Hibernate executes:

```java
new PatientInfoDTO(
        id,
        name
)
```

for every row.

---

## Advantages

* More control
* Can add custom methods
* Useful for complex responses

---

# 3. Dynamic Projection

Allows the caller to decide the return type.

Repository:

```java
<T> List<T> findBy(Class<T> type);
```

Usage:

```java
patientRepository.findBy(
        IPatientInfo.class
);
```

or

```java
patientRepository.findBy(
        Patient.class
);
```

Very flexible.

---

# Why Not Create Constructors in Entity?

Suppose we add:

```java
@Entity
public class Patient {

    private Long id;

    private String name;

    private String email;

    public Patient(
            Long id,
            String name) {

        this.id = id;
        this.name = name;
    }
}
```

Possible?

Yes.

Recommended?

No.

---

# Why Is It Bad Design?

Because Entity and DTO have different responsibilities.

Entity's responsibility:

```text
Database Mapping
```

DTO's responsibility:

```text
API Response
Custom View
Report Data
Statistics
```

Mixing both responsibilities violates good design principles.

# Why DTOs Exist

DTOs are designed for specific responses.

```text
Patient Entity
      ↓

PatientInfoDTO
      ↓

PatientAdminDTO
      ↓

BloodGroupStatsDTO
```

Each DTO serves a specific purpose.

This is the professional approach.

---

# Aggregation Projection Example

Suppose we want:

```text
Blood Group Count
```

Result:

```json
[
  {
    "bloodGroup":"A+",
    "count":10
  }
]
```

DTO:

```java
public class BloodGroupStats {

    private String bloodGroup;

    private Long count;
}
```

Repository:

```java
@Query("""
select new
com.example.dto.BloodGroupStats(
       p.bloodGroup,
       count(p)
)
from Patient p
group by p.bloodGroup
""")
```

This data cannot fit inside Patient Entity.

Hence DTO Projection is necessary.

---

# Projection vs DTO Mapping

## Without Projection

```java
List<Patient> patients =
        patientRepository.findAll();

return patients.stream()
        .map(this::convertToDTO)
        .toList();
```

Database:

```sql
SELECT *
FROM patient;
```

All columns fetched.

---

## With Projection

```java
List<IPatientInfo>
```

Database:

```sql
SELECT
id,
name,
email
FROM patient;
```

Only required columns fetched.

Much more efficient.

---

# Advantages of Projections

* Better Performance
* Reduced Memory Usage
* Less Network Traffic
* Faster Queries
* Cleaner API Responses
* Separation of Concerns
* Improved Maintainability

---

# Disadvantages of Projections

* Additional DTO/Interface creation
* Complex queries may require DTO projections
* Can become difficult to manage if overused

## Why not use Entity constructors instead of DTOs?

Because Entities represent database tables while DTOs and Projections represent specific views of data required by different use cases.

Mixing both responsibilities makes the design difficult to maintain.
